# Design Decisions

Architecture decisions recorded as they were made, not reconstructed afterward. Each entry: problem, decision, trade-offs, and how it was verified.

## Schema drift on CSV ingestion (bank source)

**Problem:** a bank statement is a CSV with no schema enforced by anyone. If the bank reorders columns, renames a header, or flips the meaning of Debit/Credit, an index-based parser would silently read the wrong field — a spending amount could be read as income with no visible error.

**Decision:** every concrete `BankStatementParser` (`BTParser`, `BCRParser`, `INGParser`) declares an explicit `_expected_header()`. On every `parse()`, the header read from the CSV is compared exactly against it — on mismatch, `SchemaDriftError` is raised and **the whole file is rejected**, not just the affected rows. The error message states what was expected vs. what was found (`ingestion/parsers/base.py`).

**Why fail-fast on header but fail-per-row on invalid data:** a missing or renamed column means *every* row in the file could be misread — there's no partial trust possible in a file with the wrong schema. An invalid date or an unreadable amount, on the other hand, is isolated to that row — the rest of the file stays trustworthy. That's why `parse()` returns `ParseResult(transactions, errors)`: good rows go into `raw`, corrupted rows are logged explicitly (line + raw content, via structured loguru), and the file isn't discarded entirely for one bad line. Verified in practice: a CSV with an invalid date on line 3 produced 2 valid transactions + 1 clearly logged error (`line_number: 3`, `raw_row: {...}`).

**Trade-off:** if the bank only appends a new column at the end (backward-compatible), the file is still rejected, even though the extra column could have been ignored. Strict was chosen over permissive: a false positive (rejecting a valid file) is far cheaper to investigate than a false negative (silently ingesting corrupted data into a financial warehouse).

## End-to-end idempotency

**Problem:** a daily DAG will run over the same files more than once — manual retry, container restart, or simply re-triggering after a fix. If any pipeline step isn't idempotent, a duplicate run means duplicate data in the warehouse.

**How idempotency is guaranteed at every layer, end to end:**
- **`ingest`** (raw): `RawLoader` dedups on `_row_hash` — the Airflow task itself keeps no record of already-processed files, it relies entirely on the loader being safe to re-run. Verified: a second `trigger` on the DAG left 149/149/149 rows per bank, unchanged.
- **`dbt_seed`**: reloads the category seed every time (full refresh) — safe, because the source file is static; same input, same output.
- **`dbt_snapshot`**: `timestamp` strategy on `updated_at` — if the row hasn't changed, the snapshot doesn't add a new version. This keeps SCD Type 2 correct even if the snapshot runs daily with no real category changes.
- **`dbt_run`**: `fact_financial_transactions` is incremental (`unique_key: transaction_id`) — see the dedicated entry below for the full reasoning. The rest of the marts stay `table` (full refresh), including `fact_daily_productivity` — reasoned separately there.
- **`dbt_test`**: stateless by construction — it only validates, it can't produce duplicates.

**Controlled catchup:** the DAG has `catchup=False` — on activation, Airflow schedules a single run for the most recently completed interval, not one per day since `start_date`. Tested: unpausing produced exactly one `scheduled__...` run, not a backlog of historical runs. For an explicit historical rebuild (e.g. full reprocessing after a bug), `airflow dags backfill` would be used manually, with explicit control over the date range — not left to the scheduler's default behavior.

**Why the dbt tasks are separate (`seed`→`snapshot`→`run`→`test`), not a single `dbt build`:** the Airflow UI graph shows exactly where the pipeline failed (e.g. the test, not the seed) without opening logs; each step keeps its own retry/duration history. Cost: 4 BashOperator tasks instead of one, acceptable at this scale.

## Scaling 100x

**Question:** if instead of a personal monthly statement this handled 100x the volume (hundreds of thousands of transactions/day, more sources, more users) — what would change, and what shouldn't?

**What would change:**
- **Postgres → a columnar warehouse** (e.g. Snowflake, BigQuery, ClickHouse). Postgres is an OLTP row-store; aggregations on `mart_monthly_spending` over hundreds of millions of rows would get slow. A columnar store scans only the columns a query needs, not the full row — exactly the read profile of an analytical mart.
- **Ingest → raw files in object storage (S3/GCS), then `COPY`/bulk load into the DWH**, not row-by-row `INSERT` from Python. At 100x volume, network round-trips per row become the bottleneck; batch files + native warehouse loading are orders of magnitude faster.
- **Airflow local → managed (MWAA, Cloud Composer) or a Kubernetes executor** — a `LocalExecutor` with a single worker doesn't parallelize enough at hundreds of concurrent tasks (many sources × many users); horizontal worker scaling is needed.
- **`fact_financial_transactions` from `table` (full refresh) to `incremental` with `unique_key`** — a full daily recompute, fine at a few hundred rows, becomes inefficient/costly at scale; the incremental model processes only new/changed rows.
- **Metabase H2 → a dedicated Postgres/MySQL** — the reason H2 works today (a single local user, no concurrency) disappears exactly at 100x: many users, concurrent dashboards, need for HA.

**What would NOT change — and why that's the strongest point:**
- **Kimball dimensional modeling** (fact grain, SCD Type 2 on categories, surrogate keys) — the logical schema is independent of the physical engine. Migrating `fact_financial_transactions` from Postgres to Snowflake doesn't require rewriting the business logic, only marginal SQL syntax adjustments.
- **dbt tests** (unique/not_null/relationships + the custom balance-reconciliation tests) — they validate *data correctness*, not the infrastructure they run on. Same tests, same confidence, regardless of warehouse.
- **The idempotency principle** (hash-based dedup, incremental models, controlled `catchup`) — a design principle, not an implementation tied to local Postgres/Airflow; it applies identically to any tool combination at any scale.

**Takeaway:** the separation between *modeling* (dbt, tests, grain, SCD) and *infrastructure* (local Postgres, LocalExecutor, H2) is exactly why a project built at personal scale still demonstrates the ability to reason architecturally, not just "ran some containers."

## Extending the architecture to a second source (GitHub)

**Question:** how much of what was built for the first source (a single CSV source, local files) carries over unchanged to a second source (a paginated, rate-limited API), and where does a genuinely new decision have to be made?

**What carried over identically:**
- The `ParseResult`/`RowParseError` pattern → `ExtractResult[T]`/`RecordParseError` for GitHub, made generic instead of three separate classes (Python 3.12, PEP 695).
- Dynamic task mapping in Airflow (`ingest.expand(source=sources)` in `bank_pipeline`) → identical in `github_pipeline` (`ingest_commits_and_pull_requests.expand(repo_full_name=repos)`) — one task per unit of work, in parallel, without knowing the count up front.
- The dbt convention: `stg_<source>__<entity>`, per-source tags in `dbt_project.yml`, standard tests (unique/not_null/relationships) + at least one `dbt_expectations` test.

**What had to be reasoned through again, not copied:**
- **Idempotency.** `raw.bank_transactions` dedups on a content hash, because a CSV statement has no natural key — two identical rows *are* the same transaction. GitHub has real natural keys (`sha`, `repo_id`, `pr_id`), but that surfaced a distinction the bank source didn't have: some entities are **immutable** (a commit never changes — dedup on key, same as bank) and others are **mutable** (a PR goes open→merged, a repo gets a new `pushed_at` — this needs `UPSERT`, not `ON CONFLICT DO NOTHING`, otherwise `raw` would freeze the first state seen and misreport the current state). Same "idempotency," two different SQL implementations, chosen based on the semantics of the source, not applied mechanically.
- **Fact grain.** `fact_financial_transactions` and `fact_daily_productivity` are both *sparse* (a real transaction / a day with real activity), consistent with Kimball. But the combined mart (`mart_daily_finance_productivity`) needed to be *dense* — a day with no commits and no spending is still a valid data point for a correlation, not a missing row. This only became clear while trying to answer "are there any funny correlations?": without explicit zero-days, any spending-vs-commits chart would be mute on exactly the interesting days.
- **Which dimension gets SCD2 and which stays Type 1.** `dim_expense_category` has SCD2 because "what category did a transaction have *then*" matters for any historical report. `dim_repository` stayed Type 1 (latest state, no history) — not because SCD2 was impossible, but because the history of a repo's `language`/`pushed_at` doesn't answer any analytical question in this project. SCD2 isn't implicitly "more correct" — it's a cost (more rows, validity-range joins) paid only when history is actually used.
- **One new abstraction, only once real duplication appeared.** `dags/common.py` (Discord alert + tagged dbt command) was extracted from `bank_pipeline.py` only once `github_pipeline.py` needed the exact same code — not preemptively. The kind of decision you can justify concretely: "moved it to a shared module because the second use proved it was generic, not because it seemed like a good idea in advance."

**A real bug caught through testing, not hypothetical:** with `GITHUB_TOKEN` set but empty in `.env` (variable present, empty value — not missing), `os.environ["GITHUB_TOKEN"]` doesn't raise `KeyError`; the error only surfaced much later, inside `httpx`, as `LocalProtocolError: Illegal header value b'Bearer '` — technically explicit (nothing passes silently), but useless for debugging. `GitHubConfig.from_env()` now explicitly validates emptiness too, not just absence — the same "fail fast, clear message" philosophy as `SchemaDriftError`, this time applied at configuration, not parsing.

**Takeaway:** the architecture held — nothing from the first source had to be rewritten, only extended. But "extensible" didn't mean "everything identical": the points where the second source genuinely differed (mutability, grain, need for history) required explicit decisions, not a mechanical copy of the bank pattern. That's the mark of a good abstraction: reuse where the problem is the same, a new decision where it isn't.

## Best-effort alerts vs. hard failure (financial alerts feature)

**Why this feature:** the original plan called for a third data source (fitness tracking) at this point. A fitness source wasn't used, so it wouldn't have added real value. Time went instead into a feature actually used day to day: getting notified when a budget is exceeded, a balance is low, or an unusually large transaction occurs — and it forces a design distinction a purely performative project could easily skip.

**The problem to design for:** where's the line between "an error here must stop the pipeline" and "an error here is just an isolated failure, the rest of the run stays valid"? There was already a precedent — the Discord failure alert (`notify_discord_failure`) — but there the alert announced a failure that had *already happened*; here the alert itself is the part that can fail, while the core pipeline (ingest → dbt) already succeeded.

**Decision:** `check_alerts` runs *after* `dbt_test`, not in parallel and not before — the data must already be validated before checking thresholds against it, otherwise alerts could fire on suspect data. `EmailSender.send()` catches any `Exception` (SMTP down, wrong credentials, timeout) and only logs it — the Airflow task still reports `SUCCESS`. `AlertConfig.from_env()` doesn't raise `ValueError` on missing SMTP config, unlike `GitHubConfig.from_env()`, which genuinely must stop ingestion if the token is missing.

**Why a failing dbt test and an unsent email aren't treated the same:** a failing dbt test means the data in the warehouse might be wrong — a balance doesn't reconcile, a category has no valid key. Continuing past that would propagate the error into anything reporting on it afterward. An unsent email says nothing about data correctness — it only means the user wasn't notified this time. The severity differs, so the pipeline's reaction has to differ too; treating every error equally harshly ("any exception stops the DAG") would be simpler to write, but would stop a healthy pipeline over an SMTP issue unrelated to data quality.

**Verified live, not just with unit tests:** rebuilt the Airflow image, `airflow dags list-import-errors` → none, `airflow tasks list bank_pipeline --tree` → `check_alerts` correctly appears after `dbt_test`, `airflow tasks test bank_pipeline check_alerts <date>` → `SUCCESS`, connected to the real Postgres, structured JSON log, "0 alerts triggered" (correct — the synthetic data has no rows on the current date).

**Takeaway:** "best-effort" isn't an excuse for sloppy code — it's an explicit decision, with a reason (alerting isn't a precondition of data correctness) and an implementation that actually honors it (the exception is caught explicitly, not accidentally swallowed). The difference between `dbt_test` (must stop the pipeline) and `check_alerts` (must not) isn't "one matters more" — it's that their failures mean fundamentally different things.

## CI with GitHub Actions

**Why now, and why not a third data source first:** the original plan put a third data source before CI. The order was reversed — CI pays off immediately (any future regression, on any change, is caught automatically), while an unused fitness source would only have added a superficial talking point.

**The core problem:** the project runs locally against a Postgres with state accumulated over time (months of synthetic data generated, re-ingested, re-run). Tests — including `integration` tests that hit a real Postgres — needed to pass starting from zero too, not just on the author's machine. Without a clean environment on every run, a bug depending on leftover state would go unnoticed locally and only surface for someone else (or after a reinstall).

**Decision: a service container, not `docker compose up`.** GitHub Actions offers job-level `services:` — a container started *only for that job's duration*, with its ports published to the runner, then destroyed automatically. A `postgres:16` service (same version as `docker-compose.yml`, but a fully isolated instance) was chosen instead of running `docker compose up` in CI — less to orchestrate (no need for Airflow/Metabase to run `ruff`/`mypy`/`pytest`/`dbt build`), faster startup, and no risk of CI implicitly depending on local `.env` files.

**A real ordering gotcha, found by trial, not assumed:** locally, `docker-compose.yml` mounts `infra/postgres/init/` as `/docker-entrypoint-initdb.d`, run automatically by the Postgres image on first start. The same trick was tried initially for the Actions service container — but service containers start during the "Set up job" phase, **before** `actions/checkout`, so the repo's files don't exist on disk yet at mount time; mounting an empty directory fails silently, it just does nothing (Postgres starts with no schema). Fix: the SQL scripts are run explicitly, as a separate step, after checkout, with `psql` directly against `localhost` (not `docker exec` — the port is already published by the service container on the runner).

**Verified locally before committing, not just "should work":** reproduced the exact CI sequence (a fresh Postgres on a separate port, the same init SQL, fake data generated, ingested, `pytest`, `dbt deps` + `dbt build`) with local Docker — 11/11 pytest tests, 64/64 dbt tests, 0 errors, starting from a completely empty Postgres. Caught a verification bug along the way (not a project bug): `docker exec ... psql -f - < file.sql` without the `-i` flag doesn't redirect stdin into the container — the command "succeeded" with no error, but ran nothing. The tell was the absence of any output ("CREATE SCHEMA" etc.) — a silent false positive, exactly the kind of bug a well-built CI pipeline should make impossible to miss.

**Takeaway:** a CI setup that just runs `pytest` without a real database tests less than it appears to — any `integration` test would silently skip itself, giving a false sense of coverage. The real challenge wasn't the YAML syntax, it was correctly reproducing, in a different execution environment, the same order of operations (schema before data, data before tests) that `docker-compose.yml` handles implicitly locally.

## First real data: a PDF statement, not CSV

**Problem:** the plan assumed the data source would always be a clean CSV exported directly from online banking. Reality: the bank provided a **PDF** statement, with no per-transaction balance column — only daily closing balances and daily turnover totals. The existing `BTParser` expects a CSV with a `Sold` (balance) column on every row. Either the parser had to change (breaking the CSV/PDF separation of sources), or the missing balance had to be reconstructed before ingestion.

**Decision: a separate converter script (`scripts/convert_bt_pdf_statement.py`), not a new `BankStatementParser`.** PDF→CSV conversion is a layout-extraction problem (x/y positions on the page), fundamentally different from parsing a fixed-schema CSV — mixing the two would needlessly complicate the `BankStatementParser` base class. The script produces a CSV *in the exact format `BTParser` expects*, then the normal ingest pipeline runs over it unchanged.

**Reconstructing the balance, with validation, not assumption:** starting from the opening balance, the signed transaction amounts are accumulated in PDF order, and at *every* day boundary the running result is checked against the bank-reported daily closing balance. On mismatch, the script stops with an error — the same fail-fast philosophy as `SchemaDriftError`, now applied to a completely different source type (layout extraction, not CSV). Independent cross-check: the computed monthly total (debit/credit) matched the PDF's reported total turnover exactly, and the same balance-continuity invariant was re-verified independently by the `assert_balance_continuity` SQL test after ingestion — two different implementations (Python at extraction, SQL after loading) confirming the same result.

**A real extraction bug, also caught by validation, not manual review:** the first assumption — "the amount sits at the end of the description block, on the last line" — turned out wrong; the actual layout places the amount on the **first line** of the transaction (next to the date), with details (REF, TID, RRN) on the following lines. With the wrong assumption, the script either dropped transactions (unattributed trailing text) or attached the wrong balances — both were flagged immediately by the per-day validation, not discovered later by inspection.

**An architecture bug found only with real data, not synthetic:** `dim_merchant`/`fact_financial_transactions` used a simple `LEFT JOIN ... ILIKE` over `merchant_rules`, with no priority. With synthetic descriptions (crafted to contain exactly one merchant name), this always worked. With real text — noisy, full of reference codes and transaction IDs, sometimes mentioning multiple platforms in the same line (e.g. a transfer fee that also mentions a betting platform) — a description could match *multiple* patterns at once, which a `LEFT JOIN` with no deduplication turns directly into **duplicate transactions** (fan-out), not just wrong categories. Fix: "first match wins," made deterministic via `row_number() over (partition by transaction_id order by priority, length(pattern) desc)`. The kind of bug that never shows up in tests with clean, self-authored data — exactly why testing against real data matters.

**New categories motivated by real transactions, not invented in advance:** `gambling`, `cash`, `fees`, `health` — the initial taxonomy (groceries/utilities/transport/dining/entertainment/transfer/income) covered the synthetic data well but completely missed real patterns (bank fees, ATM withdrawals, a gym membership). Genuinely unclear merchants (e.g. a local POS with insufficient context) were deliberately left `uncategorized`, instead of guessing — a wrong guess would be worse than an honest lack of category in a financial warehouse.

**A real, not theoretical, SCD2 trap:** the new categories initially got `updated_at = today's date` in the seed. The `timestamp` snapshot strategy set `valid_from` to that date — so no transaction from an earlier month matched them anymore in the point-in-time join in `fact_financial_transactions`, leaving `category_key` null. Fixed by setting the date back to match the rest of the taxonomy — but the `timestamp` strategy doesn't detect "I moved the date earlier" as a valid change (it only compares for "newer"), so the snapshot had to be dropped and rebuilt manually, not just fixed in the seed. The kind of SCD2 nuance that's invisible until you get it wrong once.

**Takeaway:** three different classes of bugs, caught in the same "let's load real data" session, none visible with synthetic data: (1) a wrong layout assumption, caught by the arithmetic validation built specifically because the extraction wasn't blindly trusted; (2) a latent fan-out bug in the categorization join, present since the staging/marts models were first built but unable to manifest with clean synthetic descriptions; (3) an SCD2 trap around retroactively changing `valid_from`. All three confirm the same principle: tests against your own clean data only verify that the logic works *for the shape of data you thought of* — real data is the test that counts.

## dbt unit tests, model contracts, and exposures

**Problem:** the two real bugs above (merchant fan-out, the SCD2 `valid_from` trap) were documented in prose, but nothing in the test suite mechanically "remembered" them — a normal `dbt test` checks the *result* against whatever data currently exists in the warehouse, not the model's *logic* in isolation from data state. If someone accidentally removed the `row_number()`/tie-break from a future refactor, nothing was guaranteed to fail — it would need the current data to coincidentally reproduce a pattern collision to surface again.

**Why dbt unit tests, not just data tests:** a data test (unique/not_null/relationships/dbt_expectations) runs *after* the model has materialized, against whatever is in the warehouse at that moment — it guarantees nothing about a specific case if that case isn't present in the current data. A unit test (dbt 1.8+) feeds the model fixed rows (`given`) for each `ref`/`source` it uses and checks the exact output (`expect`) — fully independent of what's in Postgres at run time. Written specifically for the two regressions: a description matching two rules at once (fee + a mentioned platform, the real case from the real statement) must produce exactly one fact row, not two; an old transaction must get the category version active *at its own date*, not the current one.

**Verified rigorously, not just written and left green:** each fix was temporarily reverted in the SQL model (removed the priority tie-break; replaced the point-in-time join with `is_current`), ran `dbt test --select test_type:unit`, confirmed the corresponding test failed with a clear diff (`actual` vs `expected`), then restored the fix. A unit test that always passes regardless of what you do to the model tests nothing — a check most portfolio projects skip entirely.

**Model contracts, a different tool for a different problem:** `contract: enforced: true` doesn't test *logic*, it tests *shape* — dbt compares the column names/types/count declared in `schema.yml` against what the model's SQL actually produces, and **refuses to write the table** if they don't match exactly (confirmed live: deliberately declared `category_name` as `integer` instead of `text`, `dbt build` failed with a clear "data type mismatch" message before any INSERT). Applied to the 4 financial marts, but for a different concrete reason per mart: on `mart_budget_alerts` because `ingestion/alerts/checker.py` reads it via raw SQL (not through another dbt model) — a rename there wouldn't be caught by *any* normal dbt test, only by a Python runtime error; on `mart_monthly_spending` because Metabase reads it directly and runs no tests at all. Unexpected side effect: enabling the contract surfaced a real dbt warning ("numeric without explicit precision, risk of silent rounding") on the aggregate columns — fixed with `cast(... as numeric(14,2))`, a higher precision than the `numeric(12,2)` used in `raw` since these are monthly aggregates, not individual transactions.

**Exposures, so the lineage graph doesn't dead-end at the last mart:** `dbt docs generate` built a complete lineage up to `mart_monthly_spending`/`mart_budget_alerts`, but showed nothing about what happens to them *after* — the Metabase dashboard and the email alerts module exist outside dbt, invisible in the graph. Two exposures (`type: dashboard`, `type: application`) explicitly declare those dependencies, with no new code — just documentation exactly where a future reader of the lineage would expect to look.

**Takeaway:** three different tools for three different problems, not a generic "added more tests" — unit tests protect *logic* from future regressions independent of data, contracts protect schema *shape* at the boundary with non-dbt consumers (Python, Metabase) that wouldn't otherwise catch a change, exposures document *who* depends on what, in the lineage where it matters. Each was actively verified to fail correctly, not assumed to work because the syntax was valid.

## mart_financial_health: periodic snapshot fact and SQL-only forecasting

**Business problem:** `mart_monthly_spending` answers "how much did I spend this month," but not more interesting questions — "how much do I have in total, across all accounts," "what percentage of income am I saving," "at this rate, how much will I spend next month." Answering those requires data the transaction fact doesn't expose directly: `balance_after` is per-transaction, per-bank, sequential — combining it into "how much do I have right now, overall" is a different modeling problem, not just a SQL aggregation.

**Periodic snapshot fact, not a transaction fact:** `fact_financial_transactions` (and `fact_daily_productivity`) are Kimball *transaction facts* — one row per real event. `mart_account_balances` is the project's first *periodic snapshot fact* — one row per (bank, month), the balance at a fixed, repeated point in time, regardless of whether any event occurred that month. The distinction matters: "stock" KPIs (account balance, inventory level) need snapshot facts, not aggregations over transaction facts, otherwise a month with no transactions would make that bank's balance "disappear" from the total, even though the money is still in the account.

**Dense grain + forward-fill (gaps-and-islands), not just the last known transaction:** for each bank, a row is generated for every month between its first and last transaction (not just months with activity), then gaps are filled with the last known balance. Postgres has no `IGNORE NULLS` on window functions (unlike some other SQL dialects), so the standard equivalent was used: `count(balance_eom)` over a chronologically ordered partition increments only on a real value (not NULL) — creating groups where every month after a real value, up to the next one, shares the same group number — then `first_value()` over that group carries the real value forward. An `is_forward_filled` column explicitly marks what's real vs. filled, so nothing (including tests) confuses the two.

**Forecast via `regr_slope`/`regr_intercept`, not a separate ML model:** these are standard Postgres aggregate functions for linear regression (least squares), usable directly as window functions with `OVER (... rows between 5 preceding and current row)` — a simple trend over the last 6 months, without leaving SQL. The real point here isn't the regression itself (trivial), it's being honest about its limitation: with fewer than 2 distinct months of data, these functions return `NULL` automatically (there's no slope to compute) — confirmed live on real data (a single month at the time): `forecast_next_month_spending` and `net_worth_trend_3m` come out `NULL`, not a made-up value or a false extrapolation from a single point.

**Verified, not just written:** a SQL reconciliation test (`assert_account_balances_match_fact.sql`) independently recomputes the end-of-month balance directly from `stg_bank__transactions`, rather than re-selecting from the mart — confirmed live to catch a regression (temporarily reversed the model's `ORDER BY`, the test failed with a clear mismatch, then restored). Plus a dbt unit test with small fixtures (a bank with transactions in two non-adjacent months, nothing in between) verifying the forward-fill behavior exactly — the gap month must appear with the prior month's balance and `is_forward_filled = true`.

## Incremental models: not everywhere, only where it's correct

**Problem:** the original architecture plan explicitly called for incremental dbt models with `unique_key` in the marts, but all marts were `+materialized: table` — full refresh on every run. At a small real transaction volume this didn't matter in practice, but it was a real gap between the declared architecture and the actual code, the kind of thing a good interviewer catches.

**What an incremental model is:** a dbt model that, on a normal run, does NOT drop and rewrite the whole table — it processes only new rows and appends them to what already exists. It matters at large volume (a full recompute becomes expensive); at small volume the difference is architectural, not a performance one.

**`fact_financial_transactions` → incremental, the rest of the marts → table, deliberately, not uniformly:**
- **The transactions fact** is the correct Kimball candidate for incremental: event grain (one transaction), append-only by construction (raw dedup on `_row_hash` guarantees a `transaction_id` never changes once created). `unique_key: transaction_id`, an `is_incremental()` filter with an anti-join (`transaction_id not in (select ... from {{ this }})`) — simple, no extra watermark column needed, so it doesn't interact with `contract: enforced`.
- **`fact_daily_productivity` stays `table`, deliberately, not out of laziness:** it re-aggregates commits + PRs per day, but `raw.github_pull_requests` is upsert (a mutable entity — a PR goes from "open" to "merged" on re-ingest). A PR merged today changes `pr_merged_count` for the day it was *created*, which can be far in the past — a naive incremental filter ("only new raw rows") would silently miss that update. A full refresh always recomputes correctly; at the current volume (dozens of commits) the cost is negligible.
- **The aggregate marts** (`mart_monthly_spending`, `mart_account_balances`, `mart_financial_health`, `mart_budget_alerts`, `mart_daily_finance_productivity`) stay `table` just as deliberately: they compute window functions (rolling average, cumulative sum, `regr_slope`) over the full history at monthly grain — a few hundred rows even with years of data. Forcing incremental logic over window functions would add real complexity (correctly recomputing part of a sliding window is non-trivial) with no benefit at this scale.

**A real gotcha found at implementation time, not in the docs:** the existing unit tests on `fact_financial_transactions` (merchant tie-break, point-in-time SCD2 join) failed on the first run with `'None' has no attribute 'database'` — a known dbt limitation: `is_incremental()` checks whether the target table *already exists* in the warehouse, and since the table already existed (from earlier runs, when it was still `table`), it evaluated to `True` and referenced `{{ this }}`, which doesn't resolve correctly inside an isolated unit test context. Documented dbt fix: `overrides: macros: is_incremental: false` on the two unit tests — explicitly forces the full (non-incremental) branch of the logic, which is what those tests actually want to verify (the categorization/SCD2 join, not the incremental filter itself).

**A trade-off worth remembering, not just theoretical:** with incremental, if `dim_expense_category` is corrected retroactively (exactly the `valid_from` SCD2 trap from the real-data session), the already-materialized fact does NOT recompute itself on a normal run — it requires an explicit `dbt run --full-refresh --select fact_financial_transactions`. This is the correct behavior (history stays fixed to what was valid *then*), but it's a conscious decision, not an implicit one — worth mentioning if asked "what do you do when a dimension changes retroactively under an incremental fact."

**Verified live, not just written:** `dbt build --full-refresh` → 81 PASS / 0 ERROR (including the 4 unit tests). Then simulated new data arriving without touching the real transactions: ingested 31 synthetic transactions → `dbt run --select fact_financial_transactions` (no full-refresh) → `INSERT 0 31` (only the new rows, the rest unchanged). Immediate identical re-run → `INSERT 0 0` (idempotent, exactly the architecture's idempotency rule). The synthetic test data was then deleted from `raw`, and `--full-refresh` correctly resynced (incremental doesn't automatically handle DELETEs from raw — another limitation worth noting, not a bug).

## dbt Semantic Layer (MetricFlow): a single definition per metric

**Business problem:** `total_spending` was already defined three times, independently, in different places — in `mart_monthly_spending`, in `mart_financial_health`, and ad hoc in native SQL for a Metabase tile. Nothing guaranteed they'd stay consistent if one changed; and any new dimension combination (e.g. "spending by category, weekends only") would have required either a new SQL model or a new native query in Metabase.

**What the Semantic Layer (MetricFlow) is:** a layer *on top of* the marts, not in their place — a metric (`total_spending`, `savings_rate`) and its dimensions (category, merchant, bank, month, weekend/weekday) are defined once, then any combination can be queried generatively (`mf query --metrics ... --group-by ...`), with no new SQL. The engine, MetricFlow, is open-source and runs fully locally (`pip install dbt-metricflow[postgres]`) — no dbt Cloud, compatible with the project's fixed stack (dbt-core + dbt-postgres).

**Why the "legacy" syntax (`semantic_models:`/`measures:`/`metrics:` with `type_params:`), not the newer inline one:** dbt 1.12 supports both, but the newer syntax (metrics declared directly under `models: - name: X / columns: [...entity/dimension...]`) hit a real parsing error (`is not valid under any of the given schemas`) — too new relative to what was correctly documented at implementation time. Reverted to the legacy syntax (still fully supported, not merely tolerated), in a separate file (`semantic_layer.yml`) — kept apart from `schema.yml` since `semantic_models:`/`metrics:` are top-level keys distinct from `models:`, with no need to live next to each model's contract/test declarations.

**`txn_date` added as a literal column on the fact, not just `date_key`:** MetricFlow requires an `agg_time_dimension` — a real time-typed column on the semantic model that holds the metrics, it can't derive time purely through an FK to `dim_date`. A small, technically motivated addition (many Kimball warehouses keep both — the surrogate FK for joins, the literal column for analytical tooling), not scope creep.

**`dim_date` reused as the time spine, not duplicated:** the Semantic Layer requires a "time spine" model (a column of consecutive days) somewhere in the project — `dim_date` (already a complete date-spine via `dbt_utils.date_spine`) is exactly that; declared with `time_spine: standard_granularity_column: date_day` in `schema.yml`, instead of creating a second model just for MetricFlow.

**`savings_rate` as a `derived` metric, not `ratio`:** the real formula is `(total_income - total_spending) / total_income`, not a direct ratio between two measures — `type: derived` allows a SQL expression over already-defined metrics. Deliberately the same formula as `mart_financial_health.savings_rate`, so the two could be checked against each other rather than assumed to match.

**A real Windows gotcha, not a project one:** `mf validate-configs`/`mf query` failed with `cannot use a string pattern on a bytes-like object`, with no useful traceback from the CLI. Calling the underlying Python classes directly worked fine, which isolated the problem to the `mf` CLI itself, not the parsing logic. A corrupted success character visible in the terminal output gave the clue: the `halo` spinner writes Unicode characters to a Windows console using the `cp1252` codepage, and the resulting encoding error gets misreported as a regex error. Fix: `PYTHONIOENCODING=utf-8` before the `mf` command — the same family of quirk as the already-known `UnicodeEncodeError` from colored `dbt` output on unit test failures.

**Verified live, not just written:** `mf validate-configs` → 0 ERRORS across all layers (manifest, semantics, warehouse: semantic models, dimensions, entities, measures, metrics). A real query: `mf query --metrics total_spending,total_income,savings_rate --group-by metric_time__month,transaction__currency` → results matched exactly what was already materialized in `mart_financial_health` for the same month (same `savings_rate` at 4-decimal rounding). Slicing by dimension through entity joins confirmed correct: by category, by weekend flag (via `dim_date`, not duplicated on the fact), by merchant.

**A detail caught on review, not on the first pass:** the first draft of the README queries didn't include `currency` in the output — a number with no unit is ambiguous in a financial project, even though the project is currently single-currency. Added `currency` as a categorical dimension on `fact_financial_transactions` in `semantic_layer.yml` (the column already existed on the fact, it just wasn't exposed semantically). A syntax gotcha found while testing: a dimension that lives directly on the queried model (not through a join to another semantic model) still requires its own entity prefix in `--group-by` — `transaction__currency`, not just `currency`. The real reason behind this, not just cosmetic: it prepares the ground for a future multi-currency source — there, a `total_spending` aggregated across currencies without distinguishing `currency` would be a data bug, not just a missing label.

## Postgres indexing, verified with EXPLAIN ANALYZE, not assumed

**Problem:** it's easy to claim "I indexed the FKs on the fact" without ever checking whether the index is actually used — especially on a personal project where the data volume never, in practice, justifies an index scan. An unused index doesn't just fail to help, it costs (space, write overhead on every INSERT/UPDATE) with no benefit.

**What was added, with a concrete reason per index, not "index everything":** Postgres indexes on `fact_financial_transactions` — `transaction_id` (unique, used directly by the incremental anti-join added in the same change: `not in (select transaction_id from {{ this }})`, run on every normal `dbt run`), `date_key`/`merchant_key`/`category_key` (standard Kimball join FKs to dimensions), `txn_date` (date-range filtering). **Deliberately no index on `source_bank`** — only 3 distinct values; with such low selectivity, any value selects on average a third of the table, and Postgres correctly picks a Seq Scan over an index regardless of volume growth — indexing a low-cardinality column is a common mistake, not a safe default.

**Verified, not assumed — this was the whole point:** `EXPLAIN ANALYZE` on a join between the transactions fact and the category dimension, filtered on category group, at the real (small) data volume → `Seq Scan` on both tables, low cost. Exactly the correct behavior: a table that fits on a single disk page has nothing to gain from an index lookup (the overhead of reading the index plus a heap fetch exceeds the cost of a linear scan over a handful of rows). A realistic volume was then simulated: temporarily ingested thousands of synthetic transactions (an otherwise-empty bank, not touching the real rows), ran `ANALYZE` for fresh planner statistics, re-ran the same query (this time filtered directly on a `category_key` value) → the planner switched to a `Bitmap Index Scan` on the `category_key` index. The synthetic data was deleted immediately after, and the fact was rebuilt with `--full-refresh` back to the real rows.

**Takeaway:** concrete evidence beats a claim — "I indexed it, and I showed with EXPLAIN ANALYZE exactly at what volume the planner actually starts using it" is a much stronger answer than "I added indexes on the FKs" with nothing behind it. And the fact that at the project's current scale the indexes sit unused isn't a problem — they're there, ready for volume, verified to work correctly when it arrives, not added by reflex.

## The Strava source: two real bugs, invisible without a real export

**Problem:** the Strava parser had been written sessions earlier, but the real export requested from Strava kept coming back empty (a one-request-per-week platform limit, plus separate device-sync issues) — so the code had only ever run against hand-written fixtures, never real data. The exact kind of gap that, for the bank source, had already produced three real bugs.

**Bug #1 — a wrongly assumed unit:** a generic `Distance` column in the export had been documented in code as "meters" — an assumption written *before* any real file existed to check it against. The first real export (3 activities, short indoor runs) showed values that were absurd as meters given the recorded elapsed time. Cross-referencing against a more detailed header block (confirmed to be in meters, verified via `elapsed_time × average_speed` on the same rows) showed the generic value was actually in **kilometers**. Fix: multiply by 1000 at parse time, with a new regression test.

**Bug #2 — an inconsistent format within the same row:** `Moving Time` is written by Strava as a float-looking string (`"66.0"`), unlike `Elapsed Time` in the same row, which is a plain integer string (`"66"`) — a simple `int()` on `Moving Time` failed instantly on the real file. No previously hand-written fixture had reproduced this, because those fixtures used "clean" values. Fix: a helper that parses through `float()` first, applied consistently to both duration columns, not just the one that failed.

**A modeling decision corrected on the spot, not just implemented as planned:** the original plan called for a `dim_activity`, mirroring `dim_repository`. During implementation it became clear an activity has **measures** (distance, calories, heart rate) — a Kimball dimension should hold descriptive attributes, not aggregatable values. Built instead as `fact_activities` (atomic grain, one row per activity, like `fact_financial_transactions`), with `activity_type` as an inline column rather than a separate dimension — the same choice made for `currency` on the financial fact.

**Takeaway:** a second concrete example in this project (after the bank source) that "I wrote a parser and it looks right" means nothing until it runs against real data — both bugs were invisible from reading the code or from self-authored fixtures, both surfaced instantly on the first real file, both were caught by validation/testing, not by manually inspecting results.

**`strava_pipeline`: a third DAG orchestrating a manual export, not a live API.** Unlike `github_pipeline` (live polling, paginated, rate-limited), the Strava source is a static file, dropped in manually, overwritten by each new export — there's no "resume point," only "last known state." `check_source` returns `None` if the file is missing, and `ingest` handles that case explicitly (returns a clear message instead of raising) — the task still succeeds, dbt runs on whatever data already exists, the same fallback pattern `bank_pipeline` uses for sample data when the private data folder is empty.

**Verified live end to end, not just via import-error checks:** rebuilt the Airflow image, triggered `strava_pipeline` manually, followed it through to success on all 4 tasks (`check_source → ingest → dbt_run → dbt_test`), confirmed from the real log output that it actually ingested the export, not just that the task succeeded empty.

**The red→green cycle, tested intentionally, same discipline as the bank pipeline:** a dbt test on activity distance was temporarily broken and the DAG re-triggered — `dbt_test` failed, `check_source`/`ingest`/`dbt_run` stayed green (exactly the expected granularity: a test failure stops the pipeline *after* ingestion already succeeded, not before), and the task log confirmed the Discord failure callback actually ran and skipped sending clearly (not silently) because the webhook URL wasn't configured in that environment. The test was restored, the DAG re-triggered, green again.

**Takeaway:** three DAGs, three different "where does the source come from" patterns (manual CSV polling, live API polling, periodic manual export), but the same shared infrastructure (`dags/common.py`: Discord alert + tagged dbt command construction) — a sign that extracting it exactly when the second pipeline needed the same code was the right call, not premature abstraction: the third pipeline reused it with zero changes.

## "Verified live" is not a test

**Problem:** an honest audit of the project (reading the actual code, not a generic checklist) found two modules that had worked correctly for several sessions — repeatedly confirmed manually, live — but had no automated test at all: `GitHubRawLoader`/`StravaRawLoader` (idempotency checked only by direct runs in Docker) and `dags/common.py` (`notify_discord_failure`/`dbt_command`, checked only via `airflow tasks test` in the real container). The distinction matters: "I ran it and it worked" is a point-in-time observation, valid for the code as it was at that moment — it doesn't stop a future regression from silently breaking that exact behavior, with neither `dbt build` nor `pytest` catching anything.

**What the new tests actually check, not just that they "don't fail":** for each mutable-entity loader (GitHub repo, PR, Strava activity), the test doesn't just verify that re-running doesn't duplicate the row — it explicitly verifies that a **changed field** (a repo's language, a PR's state after merge, a renamed activity) is correctly reflected on the next upsert. That's the real behavior an `ON CONFLICT DO UPDATE` is supposed to provide — a test that only counts rows would leave it unverified. For the immutable-entity case (`raw.github_commits`), the test verifies dedup on the natural key, symmetric with the existing test for the bank source.

`dags/common.py` turned out to be fully testable in isolation from Airflow — the module is deliberately pure stdlib (`os`/`json`/`urllib.request`), so the tests run without the heavier dependencies installed locally. `notify_discord_failure` was tested with a monkeypatched `urllib.request.urlopen`: a clean skip when no webhook is configured, a correctly built payload, and — just as important — that a network error while sending doesn't propagate the exception further (the same best-effort contract as the email alerts).

**Takeaway:** "verified live" and "covered by tests" aren't interchangeable — the first proves it worked once, at some point, with the input available then; the second proves (and keeps proving, on every `pytest` run) that it still works. The project now has both disciplines on modules that had been running correctly for several sessions on live-verification alone, precisely because an initial live check, however careful, isn't a permanent safety net.
